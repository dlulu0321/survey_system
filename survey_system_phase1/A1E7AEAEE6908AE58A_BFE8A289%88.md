# 基于 MongoDB 的问卷系统开发——第一阶段项目报告

## 一、项目目标与范围

本项目依据课程大作业第一阶段的要求，开发一个简化的在线问卷系统。注册用户可以创建、编辑、发布和管理问卷；填写者通过公开链接进入问卷并提交答案；问卷创建者可以查看统计结果。项目重点包括 MongoDB 文档建模、后端业务逻辑、条件跳转、输入校验、测试和 AI 辅助开发记录。

本报告只描述第一阶段已经设计或实现的内容。第二阶段的具体需求尚未明确，因此不提前假设第二阶段功能；当前设计为后续扩展保留空间。

## 二、系统架构与主要流程

系统采用 Flask 作为 Web 后端，HTML、CSS 和 JavaScript 实现前端交互，MongoDB 作为业务数据存储。代码按职责划分：

- `app.py`：处理 HTTP 路由、会话、权限检查和主要业务流程；
- `db.py`：负责 MongoDB 连接及索引；
- `schema.py`：定义和组织数据文档结构；
- `logic.py`：实现题目校验、条件跳转和统计逻辑；
- `templates/`、`static/`：保存页面模板、样式和前端脚本；
- `tests/`：保存自动化测试。

系统的主要业务流程为：注册/登录 → 创建问卷 → 编辑题目及跳转规则 → 发布并分享链接 → 填写问卷 → 后端校验并保存提交 → 创建者查看统计。

## 三、MongoDB 数据建模

数据库设计包含 `users`、`surveys` 和 `responses` 三个主要集合。

- `users`：保存唯一用户名、密码哈希和注册时间等信息；
- `surveys`：保存问卷所有者、公开 ID、标题、说明、匿名设置、状态、截止时间、题目数组及时间戳；
- `responses`：独立保存问卷引用、填写者 ID、答案对象和提交时间。匿名提交时，填写者 ID 可以为 `null`。

问卷题目嵌入 `surveys.questions`，便于展示问卷时一起读取题目和跳转规则。回答记录独立保存在 `responses` 中，避免问卷文档随着提交次数增加而不断膨胀。设计中使用用户名和公开 ID 的唯一索引，以及面向所有者、问卷和提交时间的查询索引。具体字段以项目中的 `数据库设计.md` 和实际代码为准。

选择 MongoDB 的主要原因是不同题型具有不同的配置字段，文档结构可以表达选项、文本长度、数字范围和跳转规则等信息。但文档数据库并不意味着不需要结构约束：系统仍需要在后端验证数据类型、必填项和取值范围。

## 四、题型、答案校验与条件跳转

第一阶段设计支持四种题型：`single`（单选）、`multiple`（多选）、`text`（文本）和 `number`（数字）。

后端校验规则包括：

- 必答题必须提供有效答案；
- 单选题答案必须属于题目配置的有效选项；
- 多选题答案应保持列表结构，并检查最少/最多选择数量；
- 文本题检查长度限制；
- 数字题检查数值格式、上下界和整数要求。

条件跳转规则保存在题目自身的 `jump_rules` 数组中，按配置顺序匹配第一条符合条件的规则。设计支持 `eq`、`contains`、`gt`、`gte`、`lt`、`lte` 等操作符，目标通过题目 ID 引用。没有规则命中时，按题目顺序继续；目标为 `null` 时结束问卷。前端负责逐题交互，后端在提交时仍需重新计算有效填写路径并校验答案，不能只依赖浏览器端的校验。

## 五、问卷状态、填写和统计

问卷状态包括 `draft`、`published` 和 `closed`。草稿不应公开填写；已发布问卷可在有效截止时间内填写；问卷关闭或超过截止时间后不应继续接受提交。非匿名问卷要求填写者登录，匿名问卷允许未登录填写，并将填写者 ID 记录为 `null`。每次提交独立保存，因此是否允许同一用户重复填写应以当前业务规则为准。

统计从原始回答记录中计算：单选题统计各选项的选择人数，多选题统计各选项被选择的次数，文本题展示回答内容，数字题展示有效数值及平均值。统计页面和相关 API 应检查问卷所有权，避免未授权用户查看结果。

## 六、近期调试与修改记录

在本机调试问卷填写流程时，发现并处理了以下问题：

1. **多选题只选择一个选项时的答案结构问题。** HTML 表单对只有一个选中项的多选题可能提交单个值，而多个选中项会提交多个值。若不区分题型进行规范化，单选值可能被错误地保存为字符串。修改方向是在后端根据题目类型处理答案：多选题始终保留列表结构，其他题型再按各自的数据格式处理。
2. **提交按钮交互问题。** 根据实际使用中遇到的问题，调整问卷填写流程，使最后的“保存回答”操作直接完成提交，避免用户还需要额外点击“下一题”才能触发提交。
3. **`app.py` 文件编辑过程中的缩进错误。** 调试时曾出现 `IndentationError`。排查方向是检查代码块缩进以及是否将局部代码片段误覆盖到整个文件中；之后重新打开并修改文件，用户反馈问卷页面上的相关问题已解决。

以上内容记录的是开发过程中实际遇到的问题及处理方向。最终提交前，仍应对当前版本执行语法检查和自动化测试，并再次手动验证单选、多选、必答、提交和统计等核心流程，确认修改没有引入回归问题。

## 七、测试方案与当前验证状态

项目包含 `tests/test_logic.py` 和 `tests/test_app.py`。测试范围设计为题目结构、条件跳转、必答校验、数字限制、多选限制、问卷创建、添加题目、发布、提交、统计、权限隔离和匿名填写。具体测试步骤以 `测试用例.md` 为准。

测试结果需要区分不同时间和不同环境：

- 早期本机开发过程中，曾有自动化测试全部通过的记录；该结果只代表当时的代码状态。
- 项目报告原记录中，生成环境执行过 Python/JavaScript 静态语法检查及逻辑单元测试，其中逻辑单元测试 6 项通过；由于当时环境缺少 Flask、PyMongo、mongomock 等依赖且无法安装，未能在该环境完成完整集成测试。
- 后续又修改了本机 `app.py` 的答案规范化和提交交互，因此不能直接把早期测试结果当作当前最终版本的测试结论。用户已反馈问卷页面上的问题得到解决，但最终版本的测试结果仍应以再次运行的输出为准。

建议在项目虚拟环境中执行：

```powershell
python -m py_compile app.py
python -m unittest discover -s tests -v
```

随后在 MongoDB 服务正常运行的情况下手动检查：创建并发布问卷、分别提交单选和多选答案（特别是多选题只选一个选项的情况）、提交文本和数字答案、验证必答及关闭状态限制、查看统计结果，并确认数据库中保存的数据结构正确。应把实际命令输出、失败项及修复结果如实补充到 `测试用例.md`，不要把尚未重跑的测试写成通过。

## 八、遇到的问题与设计考虑

1. **不同题型的数据结构不同。** 采用公共字段加题型专属字段的方式，并由后端集中校验。
2. **条件跳转与必答校验之间存在关联。** 被跳过的问题不应阻止提交，因此后端需要根据跳转规则计算实际填写路径。
3. **回答数量可能持续增长。** 将每次提交独立保存到 `responses`，避免问卷文档持续膨胀。
4. **权限不能只依赖前端界面。** 服务端需要核验问卷所有者及请求权限。
5. **表单数据可能因题型和选中数量而呈现不同形式。** 后端规范化答案时必须参考题目类型，不能简单地把所有值统一转换为字符串。
6. **代码修改可能引入回归问题。** 修复后应重新运行语法检查、自动化测试和核心流程手动验收。

## 九、第二阶段兼容性考虑

第一阶段仅实现已明确的初始需求，不对未知的第二阶段功能作出实现承诺。当前设计为后续迭代保留了以下空间：

- 核心文档保留 `schema_version`，方便将来编写数据迁移逻辑；
- 题目通过 `type` 区分题型，跳转条件采用配置化表达；
- `responses` 独立存储，方便未来增加统计维度；
- 统计可从原始提交记录重新计算，减少多处预聚合数据不一致的风险；
- 后续改动应尽量保持已有接口和字段语义，并增加回归测试。

第二阶段需求明确后，应先逐项比较新旧需求，再决定是否调整数据结构，不能提前宣称当前系统已经覆盖未知需求。

## 十、AI 辅助开发说明

开发过程中使用 ChatGPT 辅助需求拆解、架构讨论、代码起草、问题排查和文档整理。AI 生成的代码和建议需要结合本机运行结果进行核验，不能直接视为正确。本项目调试中出现过多选答案规范化和 Python 缩进问题，也说明生成或复制代码后仍需要检查题型语义、文件完整性和语法。

AI 的使用过程、人工核查和后续修改记录见 `AI使用日志.md`。日志应以实际发生的提示、修改和测试为依据；如果最终版本测试尚未重跑，应明确标记待验证，而不是补写为成功结果。
