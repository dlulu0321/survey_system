# MongoDB 数据库设计（第一阶段）

## 1. 设计原则

采用三个独立集合：`users`、`surveys`、`responses`。用户与问卷是一对多关系，问卷与填写记录也是一对多关系。问卷内的题目以数组嵌入问卷文档，回答以对象形式嵌入一次提交记录。

该方案兼顾问卷的聚合读取和回答记录的持续增长：打开问卷时通常需要一次性读取标题、说明、题目与跳转规则，因此题目嵌入 `surveys`；回答次数可能不断增加，不能将所有回答持续追加进一个问卷文档，所以每次提交单独写入 `responses`。

## 2. 集合结构

### `users`

```javascript
{
  _id: ObjectId,
  username: String,
  password_hash: String,
  created_at: Date,
  schema_version: 1
}
```

索引：`username` 唯一索引，避免并发注册产生重复用户名。

### `surveys`

```javascript
{
  _id: ObjectId,
  schema_version: 1,
  owner_id: ObjectId,
  public_id: String,
  title: String,
  description: String,
  allow_anonymous: Boolean,
  status: "draft" | "published" | "closed",
  deadline: Date | null,
  questions: [QuestionDocument],
  created_at: Date,
  updated_at: Date,
  published_at: Date | null,
  closed_at: Date | null
}
```

索引：`public_id` 唯一索引；`owner_id + created_at` 复合索引，支持用户问卷列表查询。

题目字段依题型而定，公共字段为 `id`、`title`、`type`、`required`、`jump_rules`。选项题包含 `options`；多选题额外包含 `min_select`、`max_select`；文本题包含 `min_length`、`max_length`；数字题包含 `min_value`、`max_value`、`integer_only`。

### `responses`

```javascript
{
  _id: ObjectId,
  schema_version: 1,
  survey_id: ObjectId,       // 引用 surveys._id
  public_id: String,         // 便于按公开标识排查
  respondent_id: ObjectId | null,
  answers: { question_id: answer_value },
  submitted_at: Date
}
```

索引：`survey_id + submitted_at` 支持统计时读取某问卷回答；`survey_id + respondent_id` 支持未来按填写者分析，但当前不设置唯一约束，因为需求允许同一个人多次填写。

## 3. 为什么使用 MongoDB

1. 问卷题目具有不同字段：单选/多选有选项，文本有长度限制，数字有范围限制。文档模型可以自然表达不同题型，而不必建立多张关系表并通过大量连接拼接。
2. 题目与跳转规则通常随问卷整体读取，嵌入 `surveys.questions` 能减少读取次数。
3. 回答记录数量会持续增长，因此将 `responses` 独立存储，避免问卷文档不断膨胀并接近 MongoDB 单文档大小限制。
4. 新阶段可能出现新题型、新统计维度或新跳转条件。题目是带 `type` 的文档，且包含 `schema_version`，可以在保留旧字段和旧数据的前提下扩展。

## 4. 为什么不把所有数据放在一个集合

如果用户、问卷和所有回答都混在一个文档中，会造成重复数据、文档持续膨胀、更新权限边界不清楚，并让回答统计和并发写入更困难。当前设计只在适合整体读取的题目层面采用嵌入，对用户和高增长回答采用引用与独立集合。

## 5. 数据一致性与权限

- 应用启动时创建唯一索引和查询索引。
- 用户名唯一性由数据库唯一索引兜底，而不是只依赖注册前检查。
- 所有问卷管理路由以 `owner_id = 当前登录用户 _id` 查询，不仅依赖前端隐藏按钮。
- 统计查询先验证问卷归属，再读取 `responses`。
- 每次提交保存为一条独立记录；统计从原始记录实时计算，避免维护计数器导致数据不一致。
- `schema_version` 为后续迁移提供明确的文档版本边界。


## 第二阶段新增数据集合

第二阶段新增 `question_families`、`question_versions`、`question_banks`、`question_bank_items`。题目系列保存所有者和共享关系；题目版本保存不可变的题目定义、版本号、父版本与修改说明；题库与题目版本通过关联集合连接。问卷仍嵌入题目快照，并通过 `source_question_family_id`、`source_question_version_id`、`source_question_version` 记录来源。这样题库版本变化不会反向修改已发布问卷。旧问卷因缺少来源标记，不自动进入跨问卷统计。详见 `第二阶段升级说明.md`。
